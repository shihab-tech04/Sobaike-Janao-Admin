An initial line-oriented scan found 47 Admin and 11 Public/Edge RPC names (all 58 present in the live catalog); it missed several multiline calls. A full TypeScript AST scan across both repositories then found **81 static-string RPC call sites using 72 unique function names**. The live `pg_proc` catalog had exactly one overload for each **72/72** names. Comparing supplied object keys with `pg_get_function_identity_arguments` and `pronargdefaults` yielded **0 signature-key/required-parameter mismatches among 78 directly comparable call sites**. The other three pass previously constructed argument objects: `admin_create_role`, `admin_update_role`, and `record_public_visit_session`; manual source inspection confirmed they supply the required names. The Edge submission dispatcher additionally permits three fixed RPC names (`submit_public_complaint_v2`, `submit_public_complaint_v3`, `submit_public_configured_complaint`) with identical `(jsonb,text,jsonb)` argument contracts and service-only execution. The full **75-function ABI, caller, and role-grant matrix** is in [`phase02-rpc-abi-2026-10-18.json`](./phase02-rpc-abi-2026-10-18.json). This audit establishes call-shape compatibility, **not** full behavior or authorization for all modules.

The limited local function snapshot omits 92 names, including **31 of the original 47 line-oriented Admin RPC names**, even though those functions are present in production. This is a test-fidelity and restoration-provenance gap, not evidence that the live Admin database lacks its RPCs.

## Permission and privacy evidence

- Live `complaints` has RLS enabled, authenticated `SELECT` privilege, `complaints.view` RLS policy, **no anonymous table SELECT privilege**; public reports instead go through dedicated published-only RPCs.
- Live `complaint_submission_contexts`, `complaint_responses`, `subject_responses`, `site_banners`, and `news_intake_runs` have RLS enabled and **no direct anonymous/authenticated SELECT**. `segments` and `subcategories` are public readable only via active-item policies.
- Live `admin_publish_complaint` is `SECURITY DEFINER`, executable by authenticated role only. Recovered body requires a valid `auth.sessions` row through `is_active_admin()` and requires `complaints.publish` at JWT `aal2` via `has_permission()`. Do not spoof `aal2` or weaken these gates for testing.
- Recovered reporter-context trigger scrubs coordinates and device metadata when a report exits `submitted` status. Test must verify this after genuine local publication.
- The Admin app currently has no complete MFA enrollment/challenge UI. That is an explicit Phase 09 recovery requirement, not a reason to weaken Phase 02 SQL gates.

## Additive restoration rule for missing history

The 189 missing hosted migration bodies cannot be reconstructed solely from the migration ledger, and retroactively making up their SQL would falsify provenance. Search authorized repository history/archives first (the Admin main branch and its migration-specific commit history did not contain the missing set). Retain the original hosted version ledger exactly. If the original scripts remain unavailable, build a **new, versioned, append-only forward reconciliation** derived from the current catalog and explicit contract tests; review it against clean isolated and staging databases, never `db push` the partial repository history to the hosted project, and never reset/drop/rewrite its existing ledger. All runtime changes still require their later phase gates and the separately authorized final production deployment.
